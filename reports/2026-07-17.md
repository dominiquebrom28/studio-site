**Pipeline:** frontend-dev (implementation) → qa-tester (verification + tests)

**frontend-dev** closed two real §5 gaps on the project **detail** page:
1. **Mobile reading-order fix.** Status / stack / date lived *only* in the
   right rail, which on mobile stacks *after* the entire prose body — so a
   phone reader hit all the copy before any metadata. Added a compact
   `lg:hidden` meta strip directly under the H1 (status badge with semantic
   tone, stack chips, date, and repo/live links), and made the sticky rail
   `hidden lg:block` so nothing is visibly duplicated at `lg`+. Now matches the
   brief's mobile flow: H1 → status + chips → meta row → body.
2. **"More projects" navigation.** Brief §5 asks for a "more projects mini-list
   at rail bottom" (desktop) and a "Next project / Back to all" nav (mobile).
   Added a new pure helper `getMoreProjects(slug, limit = 3)` in
   `src/content/index.ts` — returns up to `limit` *other* projects in the
   existing sorted order, **wrapping** from the current project's position so
   the last project still yields a full set; unknown slug → first `limit`.
   Rendered as a mono-eyebrow text-link list in the desktop rail bottom and in
   a mobile footer nav (with a `← All projects` link).
   Also extracted the shared `statusLabel` / `statusToneClass` maps to
   `src/content/status.ts` (were duplicated in ProjectCard).

**qa-tester** added 5 focused unit tests for `getMoreProjects` in
`index.test.ts` (excludes current slug, respects limit, wrap-around from the

## Decisions made
- **No provenance strip on project detail — deliberate, and it overrides the
  literal brief.** Brief §5's detail flow lists a `ProvenanceStrip` (the
  component exists and is wired on `BlogPost`). But the projects are honest
  write-ups of Dom's **external** repos — there is no real Judge verdict,
  commit hash, reviewer, or token count for them. Fabricating one to satisfy
  the layout would violate the studio's hard "never invent" rule, which wins.
  Left out entirely. (See open question for Dom.)
- **Kept repo/live links in the mobile meta block** even though task-2 wording
  only named status/chips/date — omitting them would strip mobile users of the
  repo/live links the rail provides on desktop (a real regression). Flagged by
  frontend-dev, accepted.
- **Right-sized to the detail page only.** The index was already on-brief;
  re-touching it would have been unrequested churn. The brief's
  "horizontally-scrollable stack chips" note on detail was left as `flex-wrap`
  (works fine at every width tested) rather than a redesign.
- QA's "redundant empty-guard" nit was reviewed and **left as-is**: the
  call-site guards wrap `MoreProjectsList` in a divider `<div>` (with a
  `border-t` on desktop), so without them an empty bordered block would render
  when only one project exists. Not redundant.

## Learnings (blog-worthy)
- **"Unchecked" ≠ "unbuilt."** The scaffold built every page forward-looking,
  so the backlog item was really about closing the gap between "renders" and
  "on-brief," not writing pages. The scheduled-run habit of *reading the actual
  code before assuming the work* is what caught this — a naive run would have
  rebuilt working pages from scratch.
- **The most valuable bug was invisible on desktop.** The mobile reading-order
  problem (metadata buried after the whole body) only shows at <1024px, and the
  build/tests were fully green with it present. It took reading the responsive
  DOM order against the brief's *mobile* flow to see it — a reminder that
  "green" doesn't mean "on-brief," and that the design brief's mobile-first
  spec is a real gate, not decoration.
- **A hard rule beat the design brief, on purpose.** The brief literally
  specifies a provenance strip on detail pages; the "never invent" rule said
  no, because these projects have no real provenance data. Two internally
  consistent studio documents can still conflict at the edges — the honesty
  rule is the tiebreaker, and that tension is itself the studio's whole pitch.
- **Extract-on-second-use paid off small.** `statusLabel`/`statusToneClass`
  were about to exist in three places (card, detail mobile strip, detail rail);
  pulling them into `content/status.ts` kept the status vocabulary in one spot
  for the inevitable future status.
