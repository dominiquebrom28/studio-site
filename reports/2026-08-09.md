# Run report — 2026-08-09

**Shape of this run: no new features. The queue was jammed and that was the
work.** Run start found **7 open PRs** (over Dom's ≤6 throttle) and **5 of them
red on `build`**. Opening an eighth would have been the wrong move twice over —
over the throttle, and adding to a pile Dom could not merge anyway. So this run
built nothing new and spent itself making the existing queue mergeable.

Result: **6 open PRs, 5 fully green and `CLEAN`**, one finishing its checks.
One PR (#113) merged mid-run off the back of the fix.

## The diagnosis

Every red PR was red for the same reason, and none of them had a real defect.

`build` runs `npx audit-ci` at `ci.yml:56`. On 2026-08-07 PR #114 fixed two
advisories (`js-yaml` GHSA-5p4m-2wfm-xmqj, then `nanoid` GHSA-2v37-7h3g-55p8)
and merged to `main`. Every branch created **before** that merge still carried
the vulnerable lockfile, so every one of them failed the audit step:

```
Failed security audit due to high vulnerabilities.
Vulnerable advisories are: https://github.com/advisories/GHSA-5p4m-2wfm-xmqj
```

The structural tell, before reading a single log: every red branch was
**exactly 3 commits behind `main`** — and those 3 commits were precisely
PR #114. The one green PR (#120) was the one branch already at `main`.

**A newly-published advisory turns the whole queue red at once, and the fix
only reaches a PR when that PR merges `main` back in.** Nobody did, for five
branches, for two days. This is the same residue the 08-07 and 08-08 items
already logged from the other end — this run is what it costs downstream.

## Two real bugs found behind the audit failure

Merging `main` in fixed the audit step on all six branches. It also uncovered
two genuine problems that the audit failure had been masking — `build` exits at
the first failing step, so nothing downstream of the audit had run in two days.

**1. A test pinned to a corpus snapshot, primed to go red on `main`.**
`check-backlog-checkoffs.test.ts` asserted
`expect(result.referencedButOpen).toHaveLength(1)`. That list is the gate's
**advisory** output — multi-PR epics, documented as never auto-failing — and it
grows by one every time a run lands a report citing a branch inside a still-open
`[ ]` item. It had grown 1 → 3 through ordinary reporting.

The important part is not that it broke here. It is that **it was going to break
on `main`**, on whichever of the queued report PRs merged first, for a reason
having nothing to do with that PR. Fixed by asserting the invariant — the known
`team/2026-08-04-runs-api` epic is still reported, `unreferenced` is still empty,
and every entry still has the right shape — instead of the count.

PR #117 had already made an equivalent fix independently, which is its own
signal: two runs, a day apart, reaching for the same repair means the
brittleness was in the assertion, not in either branch. The two rewrites were
then made **textually identical**, because two different fixes to one hunk
would have conflicted on whichever merged second — a conflict containing no
disagreement.

**2. A check-off gate that cannot see a PR number.** `backlog-checkoffs` was red
on #117 with two rows, both naming `team/2026-08-07-jsyaml-advisory` as never
referenced in `BACKLOG.md`. The work was not missing and the item was not
unchecked: the `[x]` HIGH audit item describes that lane in detail — but cites
it as "PR #114" throughout and never writes the branch name, and **the gate
matches on the branch**. A closed, ticked, correctly-reported lane read as
unreferenced. Fixed by naming the branch.

## Decisions made

**Opened zero new PRs; pushed to six existing branches instead.** The throttle
is a hard rule and the queue was already over it. Every fix this run went onto
a branch that already had a PR, so the count went *down* (7 → 6), never up.

**Put this report on the existing bookkeeping branch** rather than opening a
seventh PR for it. Same reasoning. This branch now carries three days of
bookkeeping, which is not ideal and is already logged as its own LOW item.

**Did not widen `check-report-claims`'s extractor** when it produced its first
false positive (details below). That file's header argues at length, from the
real corpus, that grading citation-vs-claim from prose is unreliable and that a
false positive there teaches people to ignore report gates. The argument holds.
Logged as a message-clarity item for Dom instead of quietly loosening a gate.

**Left `In progress` on Notion rows whose lane has an open PR**, rather than
mechanically resetting them to `Not started`. Reconciliation exists to heal
*merged* drift; a lane sitting in review is genuinely in progress, and this run
touched every one of those branches.

## Learnings

**A green audit is a measurement, not a property — and the corollary is worse
than the rule.** The 08-08 run already wrote that lesson from the *authoring*
side (a PR verified green on Monday was stale by Tuesday). This run is the
other side: a *red* audit is also just a measurement, and it stays attached to
every branch that has not merged `main` since, long after `main` itself is
fixed. Five PRs sat red for two days advertising a vulnerability that no longer
existed anywhere in the repo.

**Blocked queues hide their own contents.** `build` stops at the first failing
step, so two days of audit failure meant the test suite had not actually run on
five branches. Both real bugs this run found were sitting behind that wall —
including one primed to break `main`. A jam is not just delay; it is a period
of *unmeasured* branches that look measured, because the PR does show a red X
and everyone reads that X as "the known audit thing".

**Two runs independently reached for the same fix, which is the finding.** When
the 08-08 run and this one both rewrote the same brittle assertion without
knowing about each other, that stopped being a coincidence and became evidence
about the assertion. Worth generalising: a gate that two separate runs "fix" the
same way is mis-specified, not unlucky.

**Concurrency is real in this repo now.** Twice mid-run, a push was rejected
because another actor had moved the branch, and PR #113 merged underneath the
run. Neither caused damage — merge-and-reconcile handled both — but the
"two scheduled tasks share one checkout" item is no longer theoretical, and a
run that assumes it is alone will eventually clobber something.
