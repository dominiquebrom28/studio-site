## The thing that wasn't on the backlog

`reports/` had no `2026-08-03.md`, which under the PROJECT-BRIEF's "every run
ends with a report" rule reads as a violation. It wasn't one. The 2026-08-03
run fired, found **seven** PRs open against a stated throttle of four to six,
and correctly declined to open an eighth PR announcing that the queue was too
long. Then it pushed `team/2026-08-03-backlog-and-report` and stopped.

That branch held a 415-line run report, a HIGH backlog item (the
stale-`runs.generated.json` sequencing trap), and a genuine structural repair
to `BACKLOG.md` — a phantom `[x]` duplicate of the "QA pass is stale" item
whose entire body was a *different* item's closure note, which a merge had
wedged between that item and its own `_(…)_` paragraph. **For a day the only
record that any of this existed was a branch name.**

Two things are worth separating here. The throttle decision was right and
should not be "fixed" by relaxing it. The stranding is the defect: nothing in
this repo tracks a pushed branch with no PR. It was recovered today only
because the missing report prompted a `git branch -a` check against `reports/`
— no gate, no playbook step, and no report pointed at it. Logged HIGH, with a
draft PR as the preferred fix: visible in the PR list, excluded from review
capacity by construction.

Independently, before finding that branch, the lead had diagnosed the same
`BACKLOG.md` corruption from scratch. Two runs reaching the same conclusion
from different directions is decent corroboration that the repair is right.
The 08-03 work is folded into this PR rather than opened as its own, so it
stops being stranded without costing Dom a seventh review.

## What was done

**Runs API (#98)** — frontend-dev, against the architect's spec. `getAllRuns()`
plus the reverse join from run reports to the posts/projects they produced.
No route, no component; the sitemap staying at 30 URLs is the check that
proves it. §6 PR 3 is a hard Dom checkpoint and gates all public surface.

The join is the interesting part. The obvious implementation — derive a slug
from the report filename — **would silently join nothing**, because every
content file sets an explicit `slug:` that differs from its filename stem.
Instead it keys on the same object reference `buildCollection` already
attaches as `post.provenance`. That distinction is load-bearing for the
2026-07-16 batch, where three projects have byte-identical provenance records
but three distinct parsed objects: value equality collapses them to one,
reference identity keeps all three. Tested explicitly.

**Media dimensions (#99)** — backend-dev, then qa-tester adversarially. A
dependency-free PNG/JPEG/GIF header reader, wired into the existing asset-path
gate rather than a parallel one. Falsified red→green on real content; all 23
existing media entries already matched their files, so nothing was edited to
make it pass.

The QA pass paid for itself. Mutation testing found **three surviving
mutations** — removing progressive-JPEG `0xC2` from the SOF marker set,
loosening the `segmentLength < 2` guard, removing the `0xFF` fill-byte skip —
all of which passed the original 14 tests. The code was correct; the tests
weren't pinning it. It also found a real off-by-one in the SOF truncation
bound that produced a raw Node `RangeError` instead of the module's own
message. Silent-pass audit found nothing: an entry cannot fall through both
the path gate and the dimension gate.

**Red CI checks (#97)** — devops. A `notify-on-failure` job that comments
which check failed and the exact `gh run download` command, editing in place
on re-runs, plus the matching "download before you re-run" README step.

Sent back once on lead review. The first cut ran on fork PRs, where a
`pull_request` run gets a read-only token regardless of the `permissions:`
block — so it would 403 and go **red on every fork PR** for a reason unrelated
to the code under review. Manufacturing a permanently-red unrelated check is
precisely the failure this item exists to end. It now skips cleanly.

## The queue was red, and nobody would have known until Dom looked

After all four PRs were open, every one of them showed a failing `build` —
in about 15 seconds, far too fast for a real test run, and everything had
passed locally. It was not any lane's fault: five high-severity advisories
against `undici < 7.29.0` had been published, `main`'s audit gate had gone
red on its own, and every PR inherited it.

`undici` reaches this tree by exactly one path — `jsdom@29.1.1 → undici`, a
devDependency used as the test environment. It is not bundled and never
reaches a browser. That makes the fix low-risk; it does **not** make it
allowlistable, since all five are fixed in 7.29.0 and allowlisting a fixable
advisory is precisely how the brace-expansion entry removed on 08-03 quietly
became a real suppressed finding. One `overrides` line, `npm run audit` green.

While in that file: the react-router entry claimed **"NO FIX AVAILABLE ...
7.18.1 is the latest published release."** That has stopped being true —
`react-router` 8.3.0 now exists, above the vulnerable range. The entry stays
(still not exploitable here, and the migration is ~28 files) but its
justification was rewritten to say it is a *deferral with a known cost*
rather than an absence of options, with REVISIT trigger 1 marked as fired.
That is what the file's own STANDING LESSON demands, and this entry had
already quietly stopped honouring it.

**This is the second consecutive day a run's first real task was unjamming
the queue rather than building** — brace-expansion on 08-03, undici today.
Both times the gate went red with no change on our side, which is the gate
working as designed. Naming the pattern rather than letting it become
ambient.

One genuinely good sign: **#97's `notify-on-failure` job fired on its own
PR and passed** — the first CI failure after it landed was its own, and it
surfaced it. Unplanned end-to-end evidence for the one claim that PR could
not verify from a worktree.

## Learnings

**A correct decision can still lose the work.** The 08-03 run reasoned well
about the review queue and then left its output somewhere nothing looks. The
throttle logic and the "where does the work live" logic were never connected,
so doing the right thing produced the same outcome as doing nothing.

**Mutation testing found what a green suite hid.** 14 tests, all passing,
against correct code — and three mutations survived. "The tests pass" and "the
tests would notice if this broke" are different claims, and only the second one
matters. This is the cheapest version of that lesson this project has had.

**The obvious join would have failed silently.** Deriving a slug from a
filename produces an empty result set, not an error, on a device whose entire
purpose is verification. The failure mode this repo keeps rediscovering is not
"wrong answer" but "confident nothing."

**The same trap fired three times in three shapes.** The stale generated
artifact was a red check (PR #87), a merge conflict (this run), and a
sequencing note in a report — and it is stale *by construction* on every
report-bearing branch, because a report describes the run and so is written
after the last gate runs. That's an argument for the pre-commit hook option
rather than another playbook line.
