## What was done

### Lane 1 — PR #117 unjammed

`typecheck` was failing with six errors: `TS2304: Cannot find name
'itRealCorpus'`, `TS2552: Cannot find name 'REPO_ROOT'`, and four more of the
same shape.

The diagnosis needed no investigation, because **the file predicts its own
failure**. A tombstone at the bottom of `scripts/check-backlog-checkoffs.test.ts`
on `main` reads, verbatim:

> If you are here because typecheck says `Cannot find name 'itRealCorpus'` /
> `'REPO_ROOT'` / `'realGh'`: a merge just resurrected the block. Delete it —
> do not re-add the helpers.

The mechanism was already documented in that file's header from the first
occurrence: the branch deleted a `describe('… real corpus …')` block together
with its `REPO_ROOT` / `realGh` / `itRealCorpus` helpers and their imports;
`main` had *modified* that same block; the in-branch `git merge main` hit
delete-on-one-side / modify-on-the-other, kept `main`'s copy of the **block**
and this side's deletion of everything **around** it, and reported no conflict.

Applied the prescribed fix — 93 lines deleted, helpers not re-added. The three
tests are not lost coverage: they live in newer, corrected form in
`scripts/check-backlog-checkoffs.real-corpus.test.ts`, which the branch already
carried and which `npm run test:real-corpus` runs in CI's `backlog-checkoffs`
job.

Every gate re-run on the fixed tree before pushing: typecheck clean, 606 unit,
44 smoke, 124 component, 88 content, 3 dist-CSP, eslint 0 errors, build green,
`check-merge-revert` OK, `check-report-claims` OK, `test:real-corpus` 8/8
against real `gh`, `check-backlog-checkoffs` clean. **PR #117 is now green on
every check for the first time since it was opened.**

### Lane 2 — per-worktree Vite cache (#126)

devops was asked to prove the premise before fixing it, and to stop and report
if it turned out false. It held, and the reason it had gone unnoticed is the
interesting part: `vite.resolveConfig()` in a worktree returns
`<worktree>/node_modules/.vite`, which *looks* per-worktree — but its realpath
is `/Users/doom/…/studio-site/node_modules/.vite`, byte-identical across every
worktree, because `node_modules` is the shared symlink. The path strings differ;
the directory does not.

Fix: detect a symlinked `node_modules`, and only then set `cacheDir` to
`<root>/.vite-cache`, deliberately outside `node_modules`. A normal checkout is
untouched — verified by re-running `resolveConfig()` against Dom's real checkout
before and after, not assumed.

### Lane 4 — `safe-auto` allowlist (#128)

The pre-launch review flagged that `.test.ts` files sit in an allowlist a doc
calls "non-code", on the one lane that bypasses human review. devops verified
each sub-claim with a shell the original auditor didn't have — **and one was

The choice was measured, not argued. Across all 124 merged PRs: zero were ever

lane touched a test file. Zero realized benefit against a demonstrated
unanchored match (`scripts/anything.test.ts` was accepted — proven by executing
the real extracted guard, not by reading it). Dropped.

### Lane 5 — `check-merge-revert` path-granularity (#130)

This run generated its own reproduction. The gate reported **clean** across the
exact merge that broke PR #117, because step 3's `if (netDiffPaths.has(ownPath))
continue` exempts a path the moment it appears anywhere in the net diff — and
that file stayed present because the branch's *other* commits also touched it.
The resurrected block was never checked at all.

Decision: **document and pin, not hunk-level detection.** A content-level fix
needs a 3-way diff (no such dependency here) or a line-presence heuristic that
would fire on ordinary churn in exactly the shared high-traffic files this gap
affects. The check is in the required `build` job; a noisy version would be
worse than today's narrow, honest one. Shipped as a `KNOWN GAP` header naming
the exact line, plus a hermetic test pinning today's behaviour so a future fix
is a deliberate update.

## Learnings

**A stranded bookkeeping PR is not a bookkeeping problem — it makes the team do
duplicate work.** This is the concrete, measured cost, and it happened to this
run: a lane was dispatched to state the `e2e` lane's Chromium-only boundary,
work that merged PR #116 had *already done* — `README.md` lines 44–50 say it
plainly. The backlog read `[ ]` only because the check-off was stranded in
unmerged #117. Caught during the Notion reconciliation, after the agent had
started. Roughly an hour of an agent's work was redirected rather than wasted,
but the near-miss is the finding: **for ten days, the source of truth was
telling every reader that finished work was unfinished.** The existing item
"Notion reconciliation rule assumes the previous run's bookkeeping PR has
merged" predicted exactly this class and is now demonstrated, not theoretical.

**The mirror was more accurate than the source of truth, and the reconciliation
rule would have destroyed that.** Notion held 115 rows against `main`'s 95
items, with seven "In progress" rows carrying detailed notes on work that had
merged. The scheduled task's rule says unchecked `[ ]` → "Not started". Applying
it literally would have flattened seven information-rich rows into a status that
was *less* true. Not done; flagged instead, per the standing "if they disagree
beyond status, tell Dom rather than silently fix either side" rule.

**A comment in a file caught a bug faster than any gate did.** The 93-line fix
took minutes because a previous run wrote down not just *what* went wrong but
*what the next person should do about it*, at the exact line the problem
recurs. Every automated gate in this repo — and there are eleven — walked past
this one. Prose at the right location beat all of them.

**I introduced a factual error and an agent inherited it.** My dispatch message
asserted PR #117 "sat RED for six days, 2026-08-07 → 2026-08-13". `gh run list`
says otherwise: the branch was **green** at `a82a2f8` (08-13 08:14Z), and the
merge 43 minutes later turned it red for four days; the 08-07 → 08-13 window
belongs to PR #116. The agent wrote my wrong number into a source-code comment,
correctly attributed to me. Corrected in a follow-up commit rather than
rewritten silently. Worth recording because the direction is unusual: the
standing worry here is agents inventing facts, and this was the lead handing one
down.

**"Verify the premise before fixing it" earned its place three times.** Every
lane was told to stop and report if its item turned out to be wrong. None of
them had to — but two produced corrections that changed the work: the token
scope in the `safe-auto` finding, and the realpath mechanism behind the Vite
cache collision, which is the reason nobody spotted it from the config.
