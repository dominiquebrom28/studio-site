**Shape of this run: the throttle held, and the queue grew anyway.** Run start
found **7 open PRs** — over Dom's ≤6 throttle — and this time *all seven were
green and `MERGEABLE`*. So there was nothing to unjam and nothing to fix: the
correct move under the playbook was to build no new features, and this run

That would be an unremarkable no-op report, except for what the numbers say
when you put yesterday's next to today's. Yesterday ended at **6 open PRs**
after a run that spent itself entirely on unjamming. Today opened at **7**.
Nobody merged anything, and the queue still went up.

## The finding: this task can throttle itself to zero and the queue still grows

Three of the seven open PRs are daily logbook posts — [#118](https://github.com/dominiquebrom28/studio-site/pull/118)
(08-07), [#120](https://github.com/dominiquebrom28/studio-site/pull/120)
(08-08), [#121](https://github.com/dominiquebrom28/studio-site/pull/121)
(08-09). They were not opened by this task. They come from the separate
`daily-logbook` scheduled task, which runs at 21:30 and opens a PR every day
**unconditionally** — it has no view of the review queue and no throttle of
its own.

The consequence is structural, not incidental:

> The ≤6 throttle is enforced by exactly one of the two scheduled tasks that
> open PRs against this repo. The other one adds ~1 PR/day regardless.

So the throttle cannot actually hold the queue at 6. `studio-site-build` can
correctly decline to build — as it did today and, in effect, yesterday — and
the queue still climbs at one PR per day until Dom merges. Two of the last
three runs have now produced no feature work, and the queue went **6 → 7**
across them. The throttle is doing its job on the wrong half of the inflow.

This is a real backlog item, added below rather than acted on: changing another
scheduled task's behaviour is a process decision that belongs to Dom, and the
existing "auto-merge lane" item already says to ask before building a habit.

## Learnings

- **A throttle on one producer is not a throttle.** This task can decline to
  build perfectly and the queue still grows, because a second scheduled task
  opens PRs on a timer with no view of the queue. Rate-limiting is a property
  of a system, not of a well-behaved component in it. Two consecutive runs
  built nothing and the queue went 6 → 7.
- **"Source of truth" is a claim about a file, not about reality.** The rule
  says `main`'s `BACKLOG.md` is authoritative. `main`'s `BACKLOG.md` currently
  says a CI gate that is running on every PR in the queue is not done. When the
  bookkeeping lags the merge, following the source of truth literally
  *propagates* the lag into every downstream mirror. The fix is to check the
  merge, not the checkbox.
- **The most convincing evidence today was structural, not textual.** Nobody
  needed to read #117's diff to know the timeline fix had shipped —
  `git merge-base --is-ancestor` answers it in one call. The reports that go
  wrong are the ones that trust a checkbox over the history.
- **An absent row is worse than a wrong row.** A wrong status is visible and
  someone eventually argues with it. A missing row looks exactly like a
  complete mirror. Two instances now, both found only by hand-diffing the sets.
- **The stale-generated-artifact trap caught this run too — the fourth logged
  instance, on a run whose entire output was one report.** The first push went
  red on the `runs.generated.json` drift gate. The local `npm run build` *had*
  regenerated the file correctly; the mistake was a `git add` naming the two
  files I had consciously authored, because the third one writes itself and so
  never enters the mental list of things this run changed. Two details worth
  keeping: the local build passed and the local gates passed, because they read
  the working tree, and only CI compares the working tree to what was
  *committed* — so nothing reachable before the push could have caught it. And
  it landed on the most trivial change this repo can produce. **The trap is not
  a function of how complicated the run was; it is a function of `git add`
  taking an explicit list.** `git add -A`, or a pre-push hook running the drift
  gate against the index rather than the tree, would end this class outright.
