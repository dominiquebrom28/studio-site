### 2. Why this was a trap, not carelessness — filed as a new HIGH item

This is worth more than a one-line fix note, because the failure is structural.

`predev`, `prebuild` and `pretest` **all** run `scripts/provenance/generate.mjs`.
So any local `npm run build|test|dev` regenerates the artifact. The 08-01 run
almost certainly did run its gate. But a run report *describes the run*, so it
is written and committed **after** the last gate invocation — which means the
generated artifact is stale **by construction** on every report-bearing branch,
and the first thing that ever notices is a red check on an already-pushed PR.

Filed as a new HIGH backlog item with three costed options; recommendation is a
committed `pre-commit` hook that regenerates and stages
`src/content/*.generated.json` when `reports/*.md` is staged. `.githooks/` +
`core.hooksPath` already exist from PR #86 and already propagate to worktrees,
so it is a third script in a proven lane rather than new infrastructure.

**Second confirmed instance of the "nobody reads a red check" item.** The
existing backlog item on that subject was written 2026-07-31 about PR #69
sitting red for two days. PR #87 then sat red for two days. Same duration, same
cause, filed independently — that item should be read as load-bearing now, not
speculative.

### 6. The rebase — and two things it caught

`main` moved during this run (#87 merged), so this branch was **rebased**, not
merged — following the standing recommendation of the open in-branch-merge item
rather than repeating 2026-07-31's mistake. It conflicted in exactly the two
predicted places, and both are worth recording.

**`BACKLOG.md`.** #87 had checked off the auto-merge-allowlist item and appended
a closing note at precisely the line this run inserted its new item. Both sides
were kept. The resolution was then **verified by assertion rather than by
eyeballing it** — the check the in-branch-merge item itself recommends:

```
git diff --numstat origin/main <resolved-commit> -- BACKLOG.md   →  28  0
```

Zero removals is the whole point: the 07-31 loss was a resolution that silently
took `main`'s side and dropped 88 lines while every check stayed green.

**Use `--numstat`, not a grep for `^-`.** This run's first attempt at that proof
was `git diff … | grep -c '^-[^-]'`, which reported zero — correctly, as it
happens, but **it could not have reported anything else.** Every backlog item is
a markdown bullet starting with `-`, so a deleted item appears in a diff as
`--` and the pattern `^-[^-]` structurally cannot match it. The check was blind
to precisely the deletions it existed to catch. It was caught only because §7's
repair *did* delete a bullet and the counter still said zero. `--numstat`
reports machine-counted adds/removes per file and has no such blind spot; the
figure above is re-derived with it.

That is a small, sharp instance of this project's recurring failure shape: a
green check that verifies nothing. It is the same shape as the unset
`SMOKE_URL`, the non-blocking content gate, and the auto-merge lane guarded by a
path allowlist and no CI — and this time it was a check written *by this run,
for the express purpose of not repeating a known incident.*

**`src/content/runs.generated.json` — and a live instance of the shared-checkout
item.** Resolved by regenerating from `main`'s version rather than hand-merging
JSON. The regeneration then produced **two** new rows, not one: this report, and

checkout.** That is the open "two scheduled tasks share one working checkout and
can collide" item happening in real time, and it is the first time it has been
caught *doing* something rather than being predicted.

Committing that row would have been wrong twice over: the row belongs to another
task's report, and CI — which checks out only this branch, where that file does
not exist — would have regenerated a file without it and failed the drift gate.
So the generator was re-run with that file briefly set aside and **restored
immediately, SHA-256-verified identical**, leaving the other task untouched. The
committed artifact adds exactly one row.

**Postscript — followed through to the actual answer.** By the end of this run
`reports/maintenance-2026-08-03.md` had disappeared from the checkout entirely.
This run restored it byte-identical (SHA-256 verified) and never deleted it, and
the first read of the evidence — no file on disk, no branch containing it — was
that it was simply gone.

That read was wrong, and checking rather than reporting it settled it: the
maintenance task **committed the file to `team/maintenance-2026-08-03` and
opened PR #94** at 09:02 UTC. It left this working tree because the other task
switched branches in the checkout both tasks share. Nothing was lost.

**Checked for cross-contamination, since both tasks regenerated the same
artifact minutes apart in the same directory — and there is none.** PR #94's
`runs.generated.json` has 25 rows, contains its own `maintenance-2026-08-03`
row, and does **not** contain this run's `2026-08-03` row; its `build` passes.
This branch's artifact is the mirror image: 25 rows, this run's row, not
theirs. Both are exactly what CI regenerates on each branch independently.

So the collision was real but benign this time. The failure mode it demonstrates
is not: had either task regenerated while the other's untracked report sat on
disk — which is precisely what happened to *this* run in §6, and was caught only
by reading the diff — the committed artifact would have carried a row for a
report absent from its own branch, and the drift gate would have gone red for
reasons nothing in the PR could explain.

Neither conflict was avoidable by being careful earlier; both were caused by
concurrency this run does not control. The value is that both are now
*documented as observed*, which the shared-checkout item previously lacked —
it has been open for ten days on the strength of a prediction.

## Learnings

- **A stop condition that fires twice is a signal about the system, not the
  run.** 2026-07-31 stopped on a 7-PR queue; 2026-08-03 stopped on a 7-PR queue.
  The throttle is working exactly as designed — it is the merge rate on the
  other side of it that has not moved. Two consecutive runs have now spent
  themselves on queue maintenance instead of product.
- **"Nobody reads red checks" now has two instances, three days apart, both
  two days long.** PR #69 (07-29) and PR #87 (08-01). A backlog item written
  from one incident has been confirmed by a second. Both were diagnosable from
  evidence already sitting in CI — #69 from an artifact, #87 from a job log
  read without even re-running it.
- **Read the log before re-running the job.** #87's entire root cause was
  visible in the failed step's output, including the exact seven-line diff.
  Re-running would have cost minutes and produced the same red.
- **A reconcile rule can be locally correct and globally wrong.** Applying this
  task's own literal instruction would have degraded the mirror it was meant to
  heal. The instruction assumes `Done` means "merged"; the mirror has always
  used it to mean "work complete". Neither is wrong — they just were never
  reconciled with each other, and a rule applied without checking its premise
  would have written four false rows.
- **The queue was not indifference — it had a jam in it.** The easy reading of
  "7 PRs, throttle 4–6" is that Dom is behind. The actual reading, available
  only after looking, is that the oldest PR was mechanically blocked and one
  command fixed it; Dom merged it within minutes of it going green. Two runs
  have now stopped on queue depth, and this is the first to check *why* the
  queue was deep rather than just reporting that it was.
- **A predicted failure mode showed up mid-run and was caught by a check, not
  by memory.** The shared-checkout collision has been an open backlog item for
  ten days as a prediction. It fired during this run — another task's untracked
  report file leaked into a regenerated artifact — and what caught it was
  reading the diff before committing, not recognising the scenario.
- **"It vanished" was a wrong conclusion one command away from a right one.**
  The maintenance report file appeared to disappear from the shared checkout,
  and the honest-sounding move was to report it as undetermined. It was
  determined: the other task had committed it and opened PR #94. An admission
  of uncertainty is not automatically the accurate answer, and it costs about
  as much to check as to hedge.
- **The throttle can be blown by a task that isn't yours.** This run held itself
  to zero new PRs all day; the queue still ended at seven, because the Monday
  maintenance sweep opened one. Two scheduled tasks are budgeting against one
  shared review capacity with no visibility of each other — the existing
  shared-checkout item is really about coordination, and the shared *directory*
  is only its most visible symptom.
- **A check you write to prove you didn't repeat a mistake can itself be the
  mistake.** The `grep -c '^-[^-]'` in §6 was written specifically to prove the
  07-31 backlog loss hadn't recurred, and it was incapable of detecting a
  deleted backlog item — every item is a `-` bullet, so a deletion reads as
  `--`. It reported the right answer for the wrong reason and would have
  reported the same answer if the resolution had destroyed the file. Verifying
  work does not exempt the verification from being verified.
- **Failures that live in the gaps between gates survive all the gates.** The
  stale artifact is not caught by `typecheck`, `test`, `validate:content`,
  `verify:dist-csp-hash` or `build` — every one of them passes locally, and the
  first four *regenerate the file as a side effect*, which is precisely why the
  gap is invisible until push. Ordering, not coverage, was the defect.
