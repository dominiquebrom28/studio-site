## The finding: "all clean" is not "safe to merge in any order"

GitHub tests each PR against `main` **in isolation**. It never tests them
against each other. All ten therefore report `MERGEABLE` / `mergeStateStatus:
CLEAN` — and three of them cannot all merge without a hand-resolved conflict.

Verified empirically, not reasoned about: a throwaway clone at `main` (`ad4cde1`),
merging every PR in sequence, every order tried.

- **#112, #117 and #116 mutually conflict** on
  `scripts/check-backlog-checkoffs.test.ts`; #112 and #117 additionally conflict
  on `BACKLOG.md`. Whichever merges first, the other two go red. **No ordering
  of the three avoids it** — all six permutations were tried.
- The other seven merge clean in any order.

### #112 is superseded by #117 — close it, don't merge it

- `reports/2026-08-06.md` is **byte-identical** in both branches.
- `src/content/runs.generated.json`: #117 is a **strict superset** (+35 lines, 0
  deletions).
- `BACKLOG.md`: the only lines #117 "drops" relative to #112 are `- [ ]` rows
  that **#117 checks off**. It is the later, more complete reconciliation.
- The two branches' remaining difference is the one that matters: #112 pins
  `team/2026-08-04-runs-api` with `toContainEqual(...)`. **#117 deliberately
  removes that pin**, documenting that it went red on 2026-08-11 because
  `classify()` returns `checked` on the first `[x]` block that merely *mentions*
  a branch — so an unrelated item's checkbox silently un-reports the epic.
  Merging #112 after #117 would reinstate a known-red assertion.

Closing #112 unmerged loses nothing, removes a PR from the queue, and deletes
the `BACKLOG.md` conflict outright.

### #116's conflict is a false alarm, and resolves to "take #116"

With #112 dropped, **nine of ten merge clean** and only #116 conflicts. The
conflict is a modify/delete: #117 *edited* the real-corpus `describe` block in
`scripts/check-backlog-checkoffs.test.ts`, while #116 *deleted* it — because
#116 moves that block into a new `scripts/check-backlog-checkoffs.real-corpus.test.ts`
under its own `vitest.real-corpus.config.ts`. That is the "hermetic `npm test`"
half of #116's title.

The resolution is to **accept #116's deletion**, and it costs nothing: #116's new
file already carries #117's unpinned assertion verbatim, comment and all
(`'…no specific branch pinned — see comment'`). The fix survives the move. This
was checked rather than assumed — the failure mode worth guarding against was
exactly the opposite, a stale copy quietly reintroducing the pin in its new home.

## Learnings

- **A green check mark is a statement about one branch, not about a queue.** Ten
  PRs each individually `CLEAN` contained a three-way conflict. The per-PR signal
  is real and was never wrong; it just doesn't answer the question a reviewer is
  actually asking, which is "can I merge all of these."
- **The throttle worked, and the queue still grew** — because nothing on the
  producing side can drain it. A rate limiter on production does nothing when
  consumption is zero; it just makes the backlog build more slowly. This is the
  second consecutive run to note it (see 2026-08-10), which is itself the finding.
- **Simulating a merge is cheap enough to be routine.** A `--shared` clone,
  ten merges, a build and a test run: about a minute, and it produced a
  four-step drain order plus a lossless PR closure. Compare with discovering the
  same conflict by hand in the GitHub merge UI, three PRs deep.
- **The most valuable thing a blocked run can produce is an accurate map of the
  blockage.** The temptation was to build item #11 and add an eleventh PR to a
  queue nobody is draining.
