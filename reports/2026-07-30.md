### CLS — designer → frontend-dev (PR #78)

Two treatments because it was two bugs sharing one symptom. **(A)** cold
deep-link load: `RouteFallback` reserves `min-h-[100svh]`. **(B)** in-app
navigation: one stable `<Suspense>` around `<Outlet/>` instead of a fresh
boundary per route.

The `100svh` value is derived rather than guessed — a layout shift only counts
an element that was visible in the frame *before* it moved, so reserving one
viewport puts the already-painted `<Footer>` below the fold and its later jump
stops counting. That also explains the original symptom: CLS was ~0.39 on
*every* route regardless of content height, because the distance term saturates.
This mattered practically: the repo had measured exactly one height pair
(800px → 5096px), so any "match the typical content height" approach would have
required inventing five numbers and calling them measured.

## Learnings

**A gate that cannot see layout will bless a broken layout.** The hero lane is
the sharpest thing this run produced. Every gate passed — build, typecheck,
lint, 345 unit, 113 component, 45 content — and the component tests were
*correctly* asserting that a `<source>` element with the right media condition
existed. It did. jsdom has no layout engine, so nothing in the suite could
notice that the element it was asserting caused three quarters of the image to
be cropped away. Measured on real `dist/`: the visible fraction of the hero
drops from **0.90 to 0.26** at 375px, because every mobile asset on disk is a
375×812 portrait phone capture and the hero box is `aspect-[16/9]` with
`object-cover`. This is the *fifth* browser-only defect in this project's
history, and the first one caught **before** merge rather than after — the
Playwright lane from PR #53 is what made a five-minute check possible.

**The finding corrected the backlog item's own premise.** The item said only
recompression was blocked on missing image tooling. In fact both halves are:
usable responsive sources need mobile-width *landscape* crops, which don't exist
and can't be made without the same absent tools. A backlog item can be wrong
about its own blockers, and the way you find out is by trying it.

**Sometimes a falsification failing is the finding.** Reverting CLS treatment B
alone did *not* turn its test red, even with an injected 1500ms chunk delay —
because this app's routes are siblings at one `<Outlet/>` with identical wrapper
types, so React's unkeyed reconciliation never remounts that boundary anyway.
The honest reading is that **treatment A fixed the measured CLS and treatment B
is structural hardening whose benefit this route topology cannot demonstrate.**
Rather than ship an unfalsifiable change or quietly claim a two-part fix, the
lane added a second deterministic test that *does* catch the `key={pathname}`
regression class, and said so in the PR, the backlog and here. Two runs in a row
have now reported a falsification that failed to fail instead of burying it;
that is starting to look like a working norm rather than a one-off.

**Untested premises hide in the sentences we're proudest of.** "The generator
runs the real loader so semantics can never drift" was written into a run
report, a backlog item and a PR body, and repeated for ten days. Nothing
asserted it. The 23 tests that shipped with the feature tested the parts that
were easy to test. The claim most worth protecting was the one with no coverage
at all — worth checking, next time a design decision gets a memorable sentence,
whether the sentence has a test.

**Two items closed for the price of one, because the second was a subset.** The
draft-exclusion regression test had sat open as a P1 remnant since 2026-07-21.
It was never a separate piece of work; it was one assertion inside the
loader-contract item nobody had connected. Worth scanning the backlog for more
of these before starting a lane.

## Provenance blocks — deliberately deferred, and why

**This run's three `yaml provenance` blocks were not in this file at first.**
They were written, and the generator correctly rejected them:

```
produced path "docs/cls-fallback-decision.md" does not exist on disk
produced path "docs/reports-surface.md" does not exist on disk
produced path "scripts/generate-seo-files.test.ts" does not exist on disk
```

This was the fail-loud property from `docs/provenance-model.md` §5.2 working, not
a bug. A block is a **creation record**, and the generator verifies the created
file is actually in the tree. But every file this run created lived on a feature
branch Dom had not yet merged, while the report lived on its own branch — so at
the moment the report was written, the claim was not yet true.

Shipping the blocks anyway would have put a **red CI on a PR sitting in review
for days**, which is precisely the "a gate people learn to re-run until it's
green stops being a gate" failure this repo logged on 2026-07-19 and fixed on
2026-07-29. Inventing or forcing them was explicitly forbidden by the format's
own rules. So they were deferred, the site honestly showed "no run record" for
these entries in the meantime, and a backlog item was opened so this would not
quietly become permanent.

**This surfaced a previously undocumented ordering constraint in the provenance
format**: a run cannot record its own creations until its PRs merge. The
2026-07-27 backfill (PR #58) never hit it because it worked on already-merged
history. `docs/provenance-model.md` §13 now documents the constraint and the
standing rule for handling it.
