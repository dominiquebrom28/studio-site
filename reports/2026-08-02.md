## The correction: PR #81 was not a false claim, it was a merge eating work

The 2026-08-01 run concluded that PR #81 "claimed a file change it never made"
and called it the fourth backlog-misreports-its-own-state incident — a report
asserting something untrue about its own branch. That conclusion was reasonable
on the evidence it had (`gh pr view 81 --json files` really does return one
path). It is also **wrong on mechanism**, and I only found that because I
re-derived the incident from git instead of trusting the write-up while checking
whether PR #91's gate actually caught it.

PR #81's branch had three commits:

```
b16e7bc  Backlog + 2026-07-31 run report…    BACKLOG.md +69   reports/2026-07-31.md +283
755bf7c  Add the stale-worktree finding…     BACKLOG.md +19   reports/2026-07-31.md  +19
1e5e5e8  Merge branch 'main' into team/2026-07-31-backlog-and-report
```

The run wrote its four backlog items. Twice. Then `1e5e5e8` — an in-branch
`git merge main` timestamped **2026-07-31T10:17:48, one minute before the PR
merged** — resolved a `BACKLOG.md` conflict wholesale in `main`'s favour and
discarded all 88 lines.

The proof is a line count: `BACKLOG.md` is **1397 lines at the merge-base and
1397 lines at the branch head**. The file's net diff for the PR is therefore
empty, which is precisely why GitHub truthfully listed one changed file and why
the 08-01 run reasonably read that as "never written."

**The report was accurate when it was written.** The work existed. A merge
destroyed it eleven minutes later, and nothing anywhere went red.

### What this changes

- The 07-31 incident is **not** a fourth instance of "the backlog lies about its
  own state." It is a first instance of something else: **a merge silently
  reverting a branch's own edits.** Logged as a new HIGH item.
- PR #91's gate **still fires correctly** on the real case — run the way CI runs
  it (`merge-base...head`), the report claims `BACKLOG.md`, the branch diff is
  `reports/2026-07-31.md` only, violation. The alarm rings at the right moment;
  only the diagnosis it implies was wrong.
- But the gate is **not** the strongest available fix for the underlying
  hazard, and the item says so. A check that asserts, after any in-branch merge,
  that every file the branch's own commits touched is still present in
  `diff(merge-base, HEAD)` needs no report and no prose, and would have caught
  this the minute it happened.
- I checked the currently-open **PR #87**, which has the identical shape
  (BACKLOG edits plus an in-branch merge from `main`): **healthy** — 1428 → 1668
  lines, all four recovered items present at head. Not currently burning.

The 08-01 `RECOVERED` section keeps its original paragraph with a dated
correction appended rather than a rewrite, because how this file misread its own
history is part of the record.

## Lane 1 — report-claims gate (PR #91)

`scripts/check-report-claims.mjs` + 31 tests, wired into the **required** `build`
job. A path in a new `reports/*.md` counts as a claim only if its text block also
names **the branch's own name** — narrower than keying off an "Item worked on"
heading, because the corpus spells that heading five different ways or omits it,
and because PR #81's claim lived under "For Dom to review", under no such
heading. Extension whitelist grounded in the repo's real `git ls-files` set stops
contrast ratios, timings and semver from matching. `yaml provenance` blocks are
deliberately not re-checked — already gated. Exit code 2 means INCONCLUSIVE and
still fails CI, so it cannot become another silently-skipping gate like the
unset `SMOKE_URL`.

Five mechanisms falsified red→green. Disabling the branch-self-reference filter
alone turns 5 tests red, 3 of them real-corpus regressions. The agent also found
two genuine bugs mid-build (a list-block boundary bug that merged an unrelated
bullet's `mensapp.md` into a neighbouring claim, and a token-stripping order bug
that broke `` `profile.ts:57-64` ``).

**Lead verification:** I swept **all 24 reports** through the gate's exported
logic against the real commit that introduced each — 24/24 zero violations. A
deliberately harsher variant (test *every* branch a report names, not just its
own) flags 3 multi-lane reports, which is exactly the false-positive class the
filter exists to prevent. That is the check that proves the filter does real
work rather than being incidental.

### Coverage is thin, and saying "24/24 clean" would overstate it

Measuring what the gate actually *examined*, not just what it passed:

- Under real semantics (a report's own branch), **2 of 23 reports contain a
  single path claim the gate can see.**
- Under the most generous branch matching possible (every branch a report
  mentions), the upper bound is **7 of 24 reports, 7 claims total** across the
  entire corpus.
- It extracted **0 claims from this very report**, and the run it just gated
  reported `0 self-referential path claim(s), 0 violations`.

So on a typical report this gate is a **no-op that passes green**. That is the
exact shape of the unset `SMOKE_URL` and the once-non-blocking content gate, and
it would be dishonest to let "24/24 clean" stand without this number next to it.

Two things keep it worth merging anyway: one of the two reports it *does* see is
`reports/2026-07-31.md`, the real incident, so it covers the case that actually
happened; and the coverage is thin for a defensible reason — reports usually
name a file **or** a branch in a block, rarely both, and the alternative is
loosening the extractor into the false positives that kill gates here.

**The honest fix is a report-format convention, not a looser regex**: if the
"Items worked on" table carried the branch *and* the files each lane produced in
the same row, the gate would see every claim in every report. Not done this run
— it is a change to the report format, which is Dom's to ratify, and it belongs
next to the §14 conventions rather than smuggled into a CI PR. Flagged in PR #91
and to Dom below.

## Lane 3 — provenance §14 (PR #89)

Decision: **accept the gap**, zero code. The frame that decides it: exactly one
field in a `ProvenanceRecord` is git-derived (`commit`); the rest are asserted
and merely typed. So the feature rests on one narrow always-checkable claim, and
any option making an edit *renderable* without a comparable check inverts it.

It also names a hazard nothing in CI can catch: listing an **edited** file under
`produced:` does not error — it silently resolves an earlier run's creation
commit and ships a green build carrying a false claim, because the duplicate-path
guard only fires when another report already claimed that path, and none ever
has. The convention is the only guard, which is why §14.7 is binding.

Six options rejected in writing. (C) `modified:` anchored to a PR number was the
closest call — it genuinely keeps falsifiability, so it lost on cost, with an
explicit §14.8 revisit trigger rather than being nailed shut.

I verified every load-bearing code claim, including two that carry the argument:
**4 of the 15 existing records already render nowhere** (`loader.ts` globs only
`content/posts` + `content/projects`), and squash-merge really does break
date-scoping (`runId: 2026-07-19-evening` → commit dated `2026-07-20T21:39:38`).

## Learnings

- **Re-derive the incident, not the write-up.** Two days of reasoning rested on
  `gh pr view --json files`, which was telling the truth about a state that a
  merge had created after the fact. The evidence that broke it open was a line
  count on two refs. The previous run's conclusion was reasonable and wrong, and
  the only way to find that was to go back to git.
- **A gate can fire correctly for the wrong stated reason.** PR #91 catches
  PR #81. It just would have pointed the reader at "you didn't do the work"
  instead of "a merge ate your work." Worth remembering when a gate's
  justification story and its actual behaviour are written by the same run.
- **The strongest fix for a hazard is often not the item you opened.** The
  claims gate needs a report and prose; the merge-drop check needs neither and
  fires at the moment of damage. Both are worth having, but only one of them was
  on the backlog.
- **Deriving a value can silently cost you the copy.** Every headcount surface
  was correct after the headcount lane, and one public sentence was worse. The
  mocked-count test could never have caught it, because it asserts the number.
- **"All green" is not a coverage number.** The claims gate passes 24/24
  reports, and it examines 2 claims in 23 of them. Both sentences are true and
  only one of them is informative. Measuring what a new gate *looked at* — not
  just what it returned — should be a standing step; it is the difference
  between this gate and `SMOKE_URL`, which also passed everything.
- **The binding answer often already exists.** The headcount item read as an
  open question; `persona-bible.md` §35 had answered it unambiguously before the
  contradiction ever appeared. The failure was two surfaces hardcoding a value,
  not a missing decision.
