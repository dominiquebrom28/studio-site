## 2. Verified drain order — and this time the answer is "it's clean"

GitHub tests each PR against `main` **in isolation** and never against the
others, so "all eight are CLEAN" does not by itself mean they can merge in any
order. On 2026-08-12 that distinction mattered a great deal: three of ten PRs
mutually conflicted while all ten showed CLEAN. The check was therefore re-run
from scratch rather than assumed to repeat, in a throwaway clone at `main`
(`73c9214`) — the real checkout was never used for it.

**Result: 0 of 28 pairs conflict.** The full 8-way sequential drain was then
performed for real, and every step was a clean `ort` merge with no conflict
markers — including the three separate appends to
`src/content/runs.generated.json` (#129, #117, #131), which git resolved
automatically.

**One dependency, not a conflict: #131 subsumes #117.**
`git merge-base --is-ancestor` confirms #117's tip (`9fce67e`) is a direct
ancestor of #131's branch; #131 is #117 plus its own commits. Merging #117 first
keeps #131's reviewable diff small; merging #131 alone reaches the same tree and
leaves #117 to be closed as subsumed. That is a bookkeeping preference, not a
technical one.

## 3. What the jam has done to the bookkeeping gates

The queue is not merely slow; it has started disabling the checks that exist to
notice its side effects. Three findings, in increasing order of how much they
should change Dom's mind about draining.

**(a) Four items shipped on 2026-08-13 still read `[ ]` today.** PR #116 merged
five days ago and delivered four backlog items' worth of work. Each deliverable
was verified present on `main` this run — the real-gh test split, 
`scripts/check-clean-checkout.mjs`, the README's Chromium-only statement,
and the corrected `loader.ts` comment. All four items remain unchecked, because
their check-offs are stranded in unmerged #117 (and only one of the four, the
`loader.ts` comment, has a check-off queued there at all). The 2026-08-17 run
already named this class and paid for it: it dispatched a lane to state the
`e2e` lane's Chromium-only boundary — work #116 had already merged — and caught
it mid-flight. **For ten days `BACKLOG.md` on `main` has told every reader that
finished work is unfinished.**

**(b) The gate built to catch exactly that is blind, and blind for a circular
reason.** `check-backlog-checkoffs.mjs` on `main` exits 0 and reports _"0 merged
branch(es) unreferenced"_. It could not have reported #116's four items: it
derives its branch list from `Item | Branch | PR` rows in `reports/*.md`, and
the report naming that branch (`reports/2026-08-07.md`) is itself stranded in
#117. The string `team/2026-08-07-gate-and-doc-truth` appears **nowhere** under
`reports/` on `main`. So the gate that exists to catch un-checked-off merged
work is switched off by precisely the condition that produces it. **Filed as a
new backlog item this run** — deliberately as a third mechanism rather than
folded into the two neighbouring items, which are about matching *inside*
`BACKLOG.md` and about a *run* duplicating work; this one is about the gate's
*input*.

**(c) The 08-12 precedent's central recommendation was overtaken, and the feared
regression did not happen.** That brief argued for closing #112 unmerged as
superseded by #117, warning that merging #112 *after* #117 would reinstate a
known-red assertion pinning `team/2026-08-04-runs-api`. In the event #112 merged
first (2026-08-12) and #117 is still open, so the ordering the warning was about
never arose. Checked rather than assumed: `main` today carries the *unpinned*
form, and `scripts/check-backlog-checkoffs.test.ts:47` documents dropping the
pin on purpose. **No regression is present.** The brief's advice was sound for
the order it anticipated; the order simply went differently.

**(d) Two HIGH items rest on a false premise, and it is the third recurrence of
the same mistake.** Both "Branch protection on `main` was never configured" and
the newer "Repo-level auto-merge is ON while branch protection is OFF" are built
on `gh api …/branches/main/protection` returning `404 Branch not protected`.
**That 404 is a known false negative**: the endpoint reports only *classic*
branch protection and is blind to *rulesets*. Checked this run against the
authoritative endpoint — `gh api
repos/dominiquebrom28/studio-site/rules/branches/main` returns three active rules
from ruleset **19140193**: `deletion`, `non_fast_forward`, and
`required_status_checks` carrying `{"context": "build", "integration_id":
15368}`. So `main` **is** protected, the `build` check **is** required, and
arming `gh pr merge --auto` would **wait for CI** rather than merge immediately —
the opposite of what the newer item concludes. The same 404 produced a HIGH that
had to be retracted in the 2026-08-10 sweep and again in the 2026-08-17 sweep;
this is the third time. **Dated `LEAD CORRECTION` notes were appended to both
items rather than editing them silently**, per this repo's standing convention,
along with the rule that should stop the recurrence: never assert anything about
`main`'s protection from the `/protection` endpoint. What survives is narrower
and real — required **review** is not configured, so anything passing `build` can
merge unreviewed. Notably, the newer item's own closing caveat said the claim
"should be confirmed before anyone relies on it either way"; confirming it
falsified it.

## Addendum, same day — the queue was drained, and the merge rule changed

Everything above was written while the queue stood at eight and the standing
rule was that Dom merges. Both facts changed within the hour, so the sections
above are left exactly as written and corrected here rather than edited.

**Dom delegated merge authority for this repository, in full:** _"YOU + the team
is in full control. that is the whole point. so everything in this repository is
up to YOUR judgement to merge."_ The trigger was the honest version of the
throttle problem — 124 PRs hand-merged in 34 days, and a queue that had jammed
at 8 twice in a week.

**The queue is now empty.** Dom merged #117 himself at 13:19Z; the Project Lead
merged the remaining seven in the verified order from §2 — #126, #128, #130,
#127, #132, #129, then #131 (this PR) last. The drain ran exactly as simulated:
no conflicts, no hand-resolution, nothing unexpected.

**Worth recording against §2's own claim:** the simulation predicted a clean
8-way drain and the real drain was clean. That is the first time this repo has
verified a drain in advance and then executed it — the 2026-08-12 brief did the
verification and never got to execute.

**§3(b) was confirmed the hard way, within minutes.** The moment the seven
merges landed and their reports reached `main`, `check-backlog-checkoffs` went
**RED** — four merged branches with no check-off (#126, #127, #128, #130). That
is precisely the blindness described above: the gate had been reporting "0
unreferenced" all week *because its input was stranded*, and it started working
the instant the input came back. All four were reconciled in this PR before it
merged: three checked off with dated closing notes, and **#127 deliberately left
`[ ]`** — its work is §6 PR 3 of a multi-PR epic whose route has not shipped, so
it is now correctly reported as `referencedButOpen` rather than closed. Checking
it off would have been the exact failure the gate exists to catch.

**How the three open questions resolved:**

1. **#117/#131 stack** — resolved by events, and along the recommended path:
   #117 merged first, so #131 landed only its incremental commits.
2. **The Notion reconciliation rule** — **still open, and still Dom's.** It lives
   in the scheduled-task definition *outside* this repository, which the merge
   delegation does not cover. Flagged to him directly.
3. **The two corrected protection items (§3d)** — now the team's call under the
   delegation. Left open this run rather than closed in the same breath as the
   correction: a run that both falsifies an item and closes it gives no one a
   chance to check the falsification. They will be re-scoped to the surviving
   question — whether required *review* should be configured — on the next run.

**The delegation changes what these reports are for.** Up to now a report ended
by asking Dom to review a branch. From here the branch is already merged when he
reads it, so the report is an account of a decision taken, not a request for one.
`PROJECT-BRIEF.md`'s hard rules and `CLAUDE.md` were updated in this PR to say so,
because leaving them reading "Dom reviews and merges" would have made them the
next docs that lied — a failure mode this repo has now fixed three times.

## Learnings

- **"All CLEAN" is a per-PR claim, not a per-queue one — and re-checking it was
  still right even though the answer flipped.** On 08-12 the same check found
  three mutually-conflicting PRs among ten greens; today it found zero among
  eight. Had this run reasoned from the precedent instead of re-running the
  matrix, it would have reported a conflict risk that does not exist.
- **Withholding a PR to respect a throttle can cost the work its whole
  audience.** The 08-12 drain brief was correct, thorough, and invisible: never
  opened as a PR, still stranded eleven days on. Appending to an existing
  bookkeeping PR gets the same protection without the silence.
- **A review queue does not just delay work; it disables the instruments.** The
  check-off gate reports green because its input is stranded in the queue it
  would otherwise be reporting on. This is the third "green but covering
  nothing" instance in this repo, after the unset `SMOKE_URL` and the absent
  branch protection — and the first where the blindness is *caused by* the
  backlog state rather than merely coexisting with it.
- **Ten days of `[ ]` on merged work already cost one wasted lane** (the 08-17
  Chromium-only dispatch). The cost of the jam is now measurable in agent runs,
  not just in tidiness.
- **A wrong tool can be re-confirmed indefinitely and never get closer to being
  right.** The branch-protection 404 has now been "re-verified" across three
  separate runs (2026-08-01, 2026-08-10, 2026-08-17) and produced two
  retractions and one still-live HIGH item — because every re-check ran the
  *same blind endpoint*. Re-running a command is not verification; running a
  *different* command that could falsify the claim is. The item that got this
  right was the one that wrote down "should be confirmed before anyone relies
  on it either way" — and it was still filed as HIGH in the meantime.
