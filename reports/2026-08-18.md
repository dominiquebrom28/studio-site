## 2. Verified drain order — and this time the answer is "it's clean"

GitHub tests each PR against `main` **in isolation** and never against the
others, so "all eight are CLEAN" does not by itself mean they can merge in any
order. On 2026-08-12 that distinction mattered a great deal: three of ten PRs
mutually conflicted while all ten showed CLEAN. The check was therefore re-run
from scratch rather than assumed to repeat, in a throwaway clone at `main`
(`73c9214`) — the real checkout was never used for it.

**Result: 0 of 28 pairs conflict.** The full 8-way sequential drain was then
performed for real, and every step was a clean `ort` merge with no conflict
markers — including the three separate appends to
`src/content/runs.generated.json` (#129, #117, #131), which git resolved
automatically.

**One dependency, not a conflict: #131 subsumes #117.**
`git merge-base --is-ancestor` confirms #117's tip (`9fce67e`) is a direct
ancestor of #131's branch; #131 is #117 plus its own commits. Merging #117 first
keeps #131's reviewable diff small; merging #131 alone reaches the same tree and
leaves #117 to be closed as subsumed. That is a bookkeeping preference, not a
technical one.

## 3. What the jam has done to the bookkeeping gates

The queue is not merely slow; it has started disabling the checks that exist to
notice its side effects. Three findings, in increasing order of how much they
should change Dom's mind about draining.

**(a) Four items shipped on 2026-08-13 still read `[ ]` today.** PR #116 merged
five days ago and delivered four backlog items' worth of work. Each deliverable
was verified present on `main` this run — the real-gh test split, 
`scripts/check-clean-checkout.mjs`, the README's Chromium-only statement,
and the corrected `loader.ts` comment. All four items remain unchecked, because
their check-offs are stranded in unmerged #117 (and only one of the four, the
`loader.ts` comment, has a check-off queued there at all). The 2026-08-17 run
already named this class and paid for it: it dispatched a lane to state the
`e2e` lane's Chromium-only boundary — work #116 had already merged — and caught
it mid-flight. **For ten days `BACKLOG.md` on `main` has told every reader that
finished work is unfinished.**

**(b) The gate built to catch exactly that is blind, and blind for a circular
reason.** `check-backlog-checkoffs.mjs` on `main` exits 0 and reports _"0 merged
branch(es) unreferenced"_. It could not have reported #116's four items: it
derives its branch list from `Item | Branch | PR` rows in `reports/*.md`, and
the report naming that branch (`reports/2026-08-07.md`) is itself stranded in
#117. The string `team/2026-08-07-gate-and-doc-truth` appears **nowhere** under
`reports/` on `main`. So the gate that exists to catch un-checked-off merged
work is switched off by precisely the condition that produces it. **Filed as a
new backlog item this run** — deliberately as a third mechanism rather than
folded into the two neighbouring items, which are about matching *inside*
`BACKLOG.md` and about a *run* duplicating work; this one is about the gate's
*input*.

**(c) The 08-12 precedent's central recommendation was overtaken, and the feared
regression did not happen.** That brief argued for closing #112 unmerged as
superseded by #117, warning that merging #112 *after* #117 would reinstate a
known-red assertion pinning `team/2026-08-04-runs-api`. In the event #112 merged
first (2026-08-12) and #117 is still open, so the ordering the warning was about
never arose. Checked rather than assumed: `main` today carries the *unpinned*
form, and `scripts/check-backlog-checkoffs.test.ts:47` documents dropping the
pin on purpose. **No regression is present.** The brief's advice was sound for
the order it anticipated; the order simply went differently.

## Learnings

- **"All CLEAN" is a per-PR claim, not a per-queue one — and re-checking it was
  still right even though the answer flipped.** On 08-12 the same check found
  three mutually-conflicting PRs among ten greens; today it found zero among
  eight. Had this run reasoned from the precedent instead of re-running the
  matrix, it would have reported a conflict risk that does not exist.
- **Withholding a PR to respect a throttle can cost the work its whole
  audience.** The 08-12 drain brief was correct, thorough, and invisible: never
  opened as a PR, still stranded eleven days on. Appending to an existing
  bookkeeping PR gets the same protection without the silence.
- **A review queue does not just delay work; it disables the instruments.** The
  check-off gate reports green because its input is stranded in the queue it
  would otherwise be reporting on. This is the third "green but covering
  nothing" instance in this repo, after the unset `SMOKE_URL` and the absent
  branch protection — and the first where the blindness is *caused by* the
  backlog state rather than merely coexisting with it.
- **Ten days of `[ ]` on merged work already cost one wasted lane** (the 08-17
  Chromium-only dispatch). The cost of the jam is now measurable in agent runs,
  not just in tidiness.
