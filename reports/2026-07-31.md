outran its reviewer." That reading is wrong, and the evidence says so plainly.

2026-07-18 — #10, #11, #12, #17, all with `mergedBy` = `app/github-actions`.

matched. **No PR has carried the `safe-auto` label in 12 days.**

**Both findings are logged as new HIGH backlog items, and they are sequenced:**

### 4. PR #69's red `e2e` check

PR #69 is the oldest open PR and was the **only** one of the seven carrying a
red check (`mergeStateStatus: UNSTABLE`; every other PR is `CLEAN`). Its `e2e`
job failed once on 2026-07-29 and **has never been re-run in the two days
since** — which is its own small instance of the gates-nobody-looks-at theme.

qa-tester diagnosed it from the **failing run's own artifact**, not from a
guess: `gh run download 30433103427 -n playwright-report` and then reading
`0-trace.trace` directly. (The lead independently confirmed that artifact exists
and is unexpired before accepting the analysis built on it.)

What the trace shows:

- The second `mouseWheel` — the one after Escape closes the drawer — dispatched
  at `t=8580.3ms` and returned at `t=8581.7ms`. **1.4ms**, against 19.3ms for
  the first wheel while the drawer was open.
- The `window.scrollY` reads that followed each completed in **3–6ms**, every
  ~1s for the full 5s poll window. The page was never frozen or CPU-starved.
- The failure's own accessibility snapshot shows the dialog gone and
  `"Open menu" [active]` — focus correctly returned to the trigger.

So the scroll-lock **release was working correctly**. The failure was a single
dropped/no-op synthetic wheel gesture.

That distinction is the whole point, because it decides the fix. A longer
timeout could not have helped — CI already waited the full 5s against a
demonstrably responsive page and nothing moved. What a dropped input event needs
is a retry of the *action*. The assertion now re-dispatches the wheel on each
`expect.poll` iteration instead of only re-reading `scrollY`. This does not
weaken it: if the lock ever genuinely failed to release, repeated wheels still
wouldn't scroll and the test still goes red.

**Falsification**, which is what makes this more than a plausible story:

- The "product bug" hypothesis was falsified head-on — `body.style.overflow`
  release was stress-tested under CPU throttling to **60×** via CDP and reset
  correctly in every run, *including every run that reproduced the stuck-at-0
  symptom*.
- Old pattern: **failed 4/4** at 30/40/50/60× throttle. New pattern: **12/12
  green** at the same rates.
- Post-fix: 75/75 (`--repeat-each=25`), full `e2e/` 47/47, plus lint, typecheck,
  unit, smoke and component suites green.
- **Lead re-ran the spec independently: 18/18.**

Honest gaps, reported rather than smoothed over:

- A byte-for-byte repro of the original *natural* dropped wheel on
  non-throttled hardware was never achieved — 150+ reps at normal and CI-mode
  speed produced zero failures. The throttle repro produces the same symptom and
  is fixed by the same mechanism, but it cannot be ruled out that it is a
  related-rather-than-identical trigger path.
- **This cost PR #69 its `safe-auto` eligibility.** It qualified only via the
  `*.test.ts` pattern; `e2e/mobile-drawer.spec.ts` is a `.spec.ts` outside the
  allowlist. Accepted trade — a red PR was never going to auto-merge anyway —
  but it does mean the "5 of 7" figure above is **4 of 7 as of this run's own
  change**, and it mixes a second concern into that PR. The alternative was an
  eighth PR in an already-over-throttle queue.

Pushed to the existing branch with a full explanation as a PR comment. **No new
PR was opened for it**, which was the point.

## Learnings

- **A queue-depth stop condition is a signal, not just a limit.** The throttle
  did its job — but treating "7 > 6, therefore stop" as the whole answer would
  have missed that five of those seven never needed to be in the queue. The
  interesting question wasn't "may I build?" but "why is this queue this deep?"
- **The studio keeps building gates and then not looking at them.** Three
  instances now, all the same shape: `SMOKE_URL` unset so `deployed-smoke`
  checks nothing (11 days), branch protection absent so the auto-merge CI gate
  doesn't exist (13 days), and PR #69's red `e2e` un-rerun (2 days) while six
  green PRs queued behind it. Each one reports green or reports nothing, which
  is precisely why none of them got noticed. The 2026-07-18 retrospective post
  ("What the green checkmarks missed") called this out for *tests*; it turns
  out to apply just as well to *infrastructure the team configured for itself*.
- **Automation that requires a habit will lose the habit.** The `safe-auto`
  label got applied on the day it was built and never again. Nothing broke,
  nothing alarmed, and the lane degraded to zero use in silence. Anything that
  depends on an agent remembering to do something every run should either be in
  the playbook as a numbered step or be automatic — "we'll remember" is not a
  mechanism.
- **The evidence was sitting in an artifact nobody downloaded.** The 07-29
  `e2e` failure was diagnosable the whole time — a 2MB `playwright-report`
  artifact with a full trace, unexpired, one `gh run download` away. Instead the
  check sat red for two days while six green PRs queued behind it. The
  2026-07-29 run added exactly this capability for the *smoke* suite (PR #70,
  "make failures capturable") on the theory that the next failure should be
  diagnosable; it was right, and the very next red check proved it — except the
  artifact that solved it was one Playwright's config had been writing all
  along. **Capturable is not the same as read.** The habit worth forming:
  when a check is red, download its artifact *before* re-running it, because
  a re-run destroys the cheapest evidence you will ever have.
- **"Flaky" is a conclusion, not a starting position.** The temptation with a
  once-failing test is to re-run it and move on, or to widen a timeout until it
  stops complaining. Neither would have worked here: the trace shows the page
  responding in 3–6ms for the entire 5s wait, so the timeout was never the
  constraint. Only reading the actual failure distinguished "dropped input
  gesture" from "broken scroll-lock release" — and those have opposite fixes,
  one in the test and one in product code. The backlog's own standing rule
  ("a gate that fails should be suspected as hard as the content it fails on")
  cuts both ways: suspect it, then go find out which one is guilty.
- **Cheapest run so far, by a wide margin**, and arguably one of the more
  useful: no feature code, two process findings that unblock the next several
  runs, and the queue's only red check turned green.
