## What was done

**Artifact freshness (#104)** — devops. A `pre-commit` hook that regenerates and
re-stages `src/content/{provenance,runs}.generated.json` whenever a `reports/*.md`
is staged, with a shell short-circuit so ordinary commits are a silent ~30ms
no-op. The interesting decision was **block vs. amend**: amend on success,
**block on generator failure**. That diverges from PR #86's non-blocking drift
hooks deliberately — those are non-blocking by git *mechanics* (a `post-*` exit
code cannot abort a completed action), not by choice, so `pre-commit` gets a real
decision to make. Lead review caught a gap: the filter excluded deletions, but
`runs.generated.json` is one row per file *currently* in `reports/`, so a
`git rm` staleness it just as much as an addition. Sent back, reproduced red,
fixed with both the shell and node paths reading one exported constant so they
cannot drift.

**Merge-revert detection (#103)** — devops. Walks the branch's own first-parent
chain since its merge-base and attributes any path missing from the net diff to
whichever commit touched it **last**; a merge is a violation, the branch's own
later commit is self-caused and never flagged. It found a CI trap the item did
not know about: on `pull_request` events `actions/checkout`'s HEAD is GitHub's
synthetic test-merge commit, whose **first parent is `main`, not the PR branch**,
so walking from a bare HEAD would have checked main's own history and reported
clean on every PR forever — a gate covering nothing, the exact failure class it
was built to end. It refuses to guess (INCONCLUSIVE, exit 2) rather than fall
back.

**Stranded-branch visibility (#106)** — devops. Built option (c), both halves,
because the draft-PR convention alone cannot surface strandings that already
exist. Its `strandedStalePr` category — a PR exists but none covers the branch's
*current tip* — is what catches the `buildMode` tail behind merged PR #25.

**Tail assessment (#105)** — architect. Recommends **(c), split three ways**, not
the item's (a) or (b). Also created a local `archive/2026-07-19-buildmode-tail`
tag so the commits can never be gc'd while Dom decides.

## The one that went red, and what it cost

**PR #103 failed CI on first push** — `1 failed | 484 passed`, and the failure was
its own corpus test:

```
Error: Command failed: git log --merges --format=%H|%P|%s main
fatal: ambiguous argument 'main': unknown revision or path not in the working tree
```

The test hardcoded `main` as a local ref. On a `pull_request` checkout there is
no local `main` branch — `fetch-depth: 0` provides the objects and the
remote-tracking `origin/main`, but never a local branch of that name. It passed
in every local checkout **for the wrong reason**: our checkouts happen to have
`main`.

The irony is the useful part. The lane built careful base-ref resolution *into
the script* — a candidate list ending in `origin/main` — precisely because a bare
ref cannot be trusted, and then hardcoded a bare ref in the test proving the
script works. The gate was right about its environment; its own verification was
not.

Fixed by having the test call the script's **own** exported `resolveBaseRef()`
rather than a second ad-hoc candidate list — the same one-mechanism principle
that resolved the `ACMRD` filter on PR #104. If nothing resolves it **throws**
rather than skipping, because a silently-skipping corpus sweep is the
`SMOKE_URL` shape the PR body itself argues against.

**Falsified under the real condition rather than re-pushed hopefully:** a scratch
clone was made with only the feature branch checked out, reproducing "no local
`main`". The old test fails there with the identical error; the fixed test passes
27/27 with the sweep genuinely running (8.1s, so it examined the corpus rather
than skipping), and still reports 97 / 96 clean / 1 violation / 0 inconclusive —
confirming the fix did not narrow coverage. Only then was it pushed. CI is green.

**Two process notes.** First, **PR #97's `notify-on-failure` fired in production
on its second day alive**, commenting the failing check and the `gh run download`
command — built on the theory that the next failure should be diagnosable, and
the next failure was this one. Second, the diagnosis was made from the existing
log **before** any re-run, which is the step PR #97 added to `README.md`; a
re-run would have destroyed nothing here, but the habit is the point.

## Learnings

**A gate can be correct and still cover nothing, and the second failure is
quieter than the first.** The `pull_request` synthetic-merge-commit trap would
have produced a permanently green check examining the wrong branch — indistinguishable
from health, which is the point. That is the third instance of this shape here (unset `SMOKE_URL`,
the non-blocking content gate, now this), and the first one caught *before*
shipping rather than after. The habit that caught it was giving the gate a
distinct INCONCLUSIVE state instead of a boolean.

**Arithmetic about layout is a hypothesis.** The overlap prediction was
substantially right, but only after being measured — and measurement still moved
the work twice, removing one commit from the port and widening the scope on the
other page. It also assumed the wrong rule width (800px vs. the real 720px) and
happened to survive it. The site's own history has four browser-only defects and
one feature built-and-withheld on this exact principle; this is now five for five
in favour of measuring.

**The backlog is the least-gated artifact in a repo full of gates.** Five
incidents, five different mechanisms, and the fifth arrived while the fourth was
still being written up. Content is Zod-validated, routes are smoke-tested,
generated artifacts are drift-checked, reports now have a claims gate — and the
document that says what is *done* has nothing. Worth noticing that each incident
had a different cause, so no single gate closes the class; what they share is
that the check-off is written by hand, last, by whoever is tired.

**A gate's verification deserves the same suspicion as the gate.** PR #103's
script reasoned carefully about which ref is "base" and its test hardcoded one —
so the test passed locally for a reason that had nothing to do with correctness.
The 2026-07-19 lesson was *"a gate that fails should be suspected as hard as the
content it fails on."* This is the mirror: a gate that **passes** should be
suspected as hard as the environment it passed in. The cheap habit that catches
it is reproducing the CI shape locally — a clone with only the feature branch
took under a minute and turned a guess into a red→green proof.

**"Assessed" is a legitimate way to close a decision item.** The tail sat open
two weeks because its next step was a decision nobody had information for. The
work that unblocked it was not code — it was reading 11 files and measuring two
pages. Items whose next step is "someone's call" should be read as *research*
tasks, not blocked tasks.
