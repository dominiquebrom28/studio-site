## Four claims that did not survive being checked

### 1. "I cannot run `npm audit`" — so somebody ran it

The security-auditor is read-only by charter. Its report said so explicitly:
the dependency-audit section named `npm run audit` as the one check it could
not perform and recommended someone else run it.

Somebody did, and `main` was **red**: `GHSA-5p4m-2wfm-xmqj|js-yaml`
(CVE-2026-59870 — quadratic CPU consumption resolving `!!omap` keys, CVSS 7.5,
range `>=4.0.0 <4.3.1`). This repo was on 4.3.0. The gate is
`.github/workflows/ci.yml:56`, inside the **required-candidate `build` job**, so
this was not a theoretical red — every PR opened that morning would have failed
the same step for a reason unrelated to its own diff.

Fixed immediately and separately in PR #114 (4.3.0 → 4.3.1, with the
`package.json` range moved `^4.1.0` → `^4.3.1` so the floor travels with it),
opened first and flagged "merge first" precisely so the three PRs behind it
would not each inherit a red check.

Two things about it are worth more than the bump itself.

**It is the exact inverse of the trap this project already documented.** The
logged trap is raw `npm audit` crying wolf while `npm run audit` — the gate with
the reviewed allowlist in `audit-ci.jsonc` — passes. Here the gate itself was
genuinely red. And the allowlisted `react-router` advisory
(`GHSA-qwww-vcr4-c8h2`) passing correctly through in the same run is what proves
the allowlist still **discriminates**, rather than having quietly decayed into a
blanket mute. A suppression list is only trustworthy while something still gets
through it.

**Nothing outside a PR runs this gate.** A newly-published advisory against an
already-installed dependency turns every open PR red simultaneously, and is
otherwise invisible. That is the second occurrence in four days (2026-08-04's
`undici` batch, PR #101, was the first) and it is now recorded in the backlog as
direct evidence for the P2 batch's long-parked "scheduled `npm audit`" — which
has sat there as a nice-to-have since July and is now the fix for a HIGH.

### 2. "`GH_TOKEN=` proves the suite is hermetic" — the lead's own, and it proved nothing

The MEDIUM item this run closed asked whether `npm test` should depend on a
GitHub session. The answer was no; the work was to move the real-`gh` tests out.
Verifying the move meant answering "is the default suite now genuinely
network-free?", and the lead's first check was to run it with `GH_TOKEN=`
blanked.

It passed. It meant nothing. **`gh` falls back to the local keyring**, so an
empty environment variable authenticates perfectly well on any machine where
someone has ever run `gh auth login` — which is every machine this suite has
ever been verified on. The check was structurally incapable of failing.

The real test is removing `gh` from `PATH` entirely. Doing that immediately
found what the environment-variable check had hidden: a **second** real-`gh`
block still sitting in the default suite (§3).

This is the same shape as PR #110's lesson from yesterday — a verification whose
oracle is weaker than its phrasing — and it is worth recording that the lane
that spent this run auditing other people's claims produced one of its own.

### 3. "This is the first time the default gate depends on the network" — false by one day

The backlog item's framing was that PR #110 had introduced something new: a
default `npm test` requiring network and a GitHub session.

It had not. `scripts/check-stranded-branches.test.ts` (PR #106) shipped the
identical real-`gh` corpus pattern on **2026-08-05**, one day earlier. The item
was written on 2026-08-06 by the same lead that had reviewed #106.

The premise has been **corrected in place in `BACKLOG.md`, struck through rather
than deleted**, because the wrong premise is the direct cause of the next
finding — deleting it would have erased the explanation.

**The first pass moved only the three tests the item named.** That left the
sibling's identical block in `npm test`: a default suite still requiring a
GitHub session, now with a `vitest.config.ts` `exclude` list that documented
only half the dependency. That is worse than either uniform answer, and worse
than doing nothing, because that `exclude` list is exactly the map a future run
will read to learn what touches the network. Caught in lead review after the
`PATH` test from §2; both blocks are now in `*.real-corpus.test.ts` files behind
`npm run test:real-corpus`, and `vitest.config.ts` names both.

### 4. "Moving them to the `backlog-checkoffs` job is safe — it already has `GH_TOKEN`" — it would have gone silently green

The move's whole premise was that `backlog-checkoffs` already carries the
network and session dependency, so nothing new is introduced by running the
tests there. True about the token. False about the checkout.

`backlog-checkoffs` used `actions/checkout@v4` at its defaults — **single
branch, depth 1** — with a header comment explaining at length why
`fetch-depth: 0` was unnecessary. That comment was correct about
`check-backlog-checkoffs.mjs`, which makes zero git calls. It was not correct
about the thing being moved in: `check-stranded-branches` runs
`git for-each-ref refs/remotes/origin/team refs/remotes/origin/claude`, and a
single-branch clone contains exactly one matching ref.

Measured rather than reasoned about, in two real clones of this repo:
**1 ref in the single-branch clone, 119 in a full one.** The check returned
`inconclusive` / `0 scanned` — green, and covering nothing. The
green-but-covering-nothing pattern, logged for the fourth time.

Fixed with `fetch-depth: 0` (plus the `npm ci` the vitest step needs), and the
superseded comment rewritten rather than left to mislead the next reader.
Both real-corpus files keep PR #110's hard-fail-under-CI guard, so this can
never degrade into "moved, and now runs nowhere."

## The finding no gate could ever have caught

The site's hero says an AI team builds the software. Of seven projects, exactly
one is team-built — `content/projects/studio-site.md`, the site's own entry, the
only `soloBuild: false` in the repo.

It was `featured: false`, with no `order`.

So the homepage rendered three featured cards — SoulForge, Portfolio, Chart
Token Playground — every one of them stamped **SOLO BUILD**, under a headline
claiming the opposite. The single card that proves the claim was not on the
page. The `soloBuild` flag shipped on 2026-07-24 specifically to make that
distinction visible, and it worked exactly as designed; it just had nothing to
distinguish against.

**No gate here could have caught this, and no future gate should be built to
try.** Content validates against Zod (both files are valid), routes smoke-test
(both pages return 200), CSP hashes match, contrast passes, `e2e` is green.
Every one of them is correct. "Does the front page argue for the thing the front
page says" is not a property with a schema.

It took a designer looking at the thing. That is the entire argument for the
Pre-launch review item's existence, on the run that finally closed it after
three weeks unstarted — and it is a better argument than the item itself made.
Fixed in PR #115 (`featured: true`, `order: 0`), which is a two-line diff and
the most valuable two lines of the run.

## The other half of the pre-launch review

Read-only security-auditor and read-only designer, in parallel, whole codebase.
Findings in `docs/pre-launch-review-2026-08-07.md`; the ones fixed in PR #115:

- **P1 — auto-merge could merge unreviewed code.** `gh pr merge --auto` is
  *sticky repo-side state*. Sequence: first commit touches only `content/**` →
  gets `safe-auto` → auto-merge armed. A later commit on the same PR adds
  something under `src/` → the guard correctly flags it and removes the label —
  **and auto-merge stays armed**, because removing a label does not un-arm it.
  GitHub would squash-merge the unreviewed commit the moment CI went green. The
  guard was doing its job and its job was insufficient. Now calls
  `--disable-auto` **first**, before the comment and the label removal, with the
  expected non-zero exit (nothing armed) handled explicitly rather than by a
  blanket `|| true` that would also swallow a real auth failure. The doc's
  "how to disable" section is corrected too: manually removing the label does
  **not** disarm, because GitHub does not fire this workflow on unlabeling.
- **Bot-comment fence break-out.** The guard interpolated unsafe filenames
  inside a ``` fence in its own PR comment; a filename containing a fence
  terminator escapes it. Indented block instead.
- **Indexable soft-404.** `NotFound` returned the app shell with status 200 and
  no `noindex`, so every mistyped URL was an indexable page. `Seo` gained a
  `noindex` prop with tests.
- **Design, second fix:** a TL;DR chip on `PostCard`, derived from `post.tldr`
  presence rather than a new frontmatter field, reusing `TLDRBlock`'s own
  `marker-700` tint so the card and the post read as one device. Derivation over
  a parallel flag is the designer's explicit recommendation and it cannot drift
  from whether a `TLDRBlock` actually renders.

Everything not fixed is a backlog item, not a paragraph in a review document
nobody will reopen: the `safe-auto` "non-code" mislabel, the unverified live
headers, three visual questions, drafts in the bundle, `img-src` vs the schema,
and the `gh pr diff` truncation hypothesis. Eight new items in all.

## Notion mirror

Reconciled. The **both-ways completeness check ran for the first time**, and
the interesting result is a design finding rather than a drift report.

Matched **64 Done rows against 64 `[x]` items**. Three further rows read Done in
the mirror with no `[x]` on `main` — fully explained: all three are check-offs
sitting in PR #112, which has not merged. No orphans, no silent reconciliation
needed.

**A naive both-ways title diff would have reported those three as orphans**, and
it would have been wrong every time. The mirror is updated when work *ships*;
`main` records it when the bookkeeping PR *merges*; those are always at least a
day apart, and longer while PRs queue. **The mirror legitimately runs ahead of
`main`.** Any future automation of this comparison has to take the open
bookkeeping PRs as an input, or it will manufacture a false finding on every
single run — which is the "a gate people learn to ignore" failure, pre-built.

**The `BuildTimeline` row was deliberately left "In progress"** rather than
reconciled either way. PR #111 merged, so "Not started" is false about real
shipped work — but its check-off is stranded in the unmerged #112, so "Done"
would contradict `main`, and the mirror's whole job is to agree with `main`.
"In progress" is the only value that is not a lie. It resolves itself when #112
merges. Recorded here so the next run does not read it as drift and "fix" it.

## Learnings

- **"I can't check that" is a finding, not a caveat.** The security-auditor
  named the one command it could not run, and running that command found `main`
  red. The valuable output of a read-only review is not only what it found — it
  is the explicit list of what it could not look at. That list should be treated
  as a work queue, not as a disclaimer.
- **A hermeticity check that cannot fail is not a check.** `GH_TOKEN=` felt like
  a test and was worthless, because `gh` reads the keyring. The general form —
  and this run's second instance of it after yesterday's "no new false
  positives" — is that a verification needs its oracle stated out loud, because
  the phrasing is almost always broader than the thing actually being tested.
  Removing the tool from `PATH` is a test; blanking a variable is a hope.
- **Correct half a thing and you have made it worse.** Moving one of two
  identical network-dependent blocks left the suite still non-hermetic *and*
  left `vitest.config.ts`'s `exclude` list documenting only half the dependency
  — and that list is precisely what the next run would trust. Partial fixes to
  the *map* are more expensive than partial fixes to the territory.
- **A comment explaining why something is unnecessary survives the change that
  makes it necessary.** `backlog-checkoffs` carried a careful, correct,
  well-argued paragraph on why it needed no `fetch-depth: 0` — written about a
  different script than the one later added to that job. Long justifications age
  worse than short ones, because they are more convincing when wrong.
- **The mirror is allowed to be ahead of `main`, and any check comparing them
  must know that.** Three rows that a naive title diff would have called orphans
  were simply work that shipped before its bookkeeping PR merged. A completeness
  check that does not model the in-flight PR generates a false finding on every
  run — which is how gates get ignored.
- **The best finding of the run had no gate, no test, and no schema.** A
  homepage arguing against its own headline is not a property anything here can
  assert. It cost one designer, one page load, and two lines of frontmatter. The
  three-week-old Pre-launch review item was right to exist, and it took three
  weeks to get to.
