# Run report — 2026-08-11

**Shape of this run: the queue was over throttle again, so instead of building,
I merged it — locally — and found a defect that only exists in the merge.**

Run start: **9 open PRs**, every one green and `MERGEABLE`. That is well past
Dom's ≤6 throttle, so under the playbook this run builds nothing. The 2026-08-10
run reached the same conclusion and wrote an honest no-op report. Doing that a
second time would have produced a second sentence saying nine green PRs are
still nine green PRs.

So this run spent itself on the thing actually blocking the studio: proving the
queue is safe to merge, in what order, and what breaks if you merge it the
obvious way. It turns out something does.

## The finding: the defect is in the merge, not in any PR

PR #117 replaced a snapshot assertion in `scripts/check-backlog-checkoffs.test.ts`:

```
expect(result.referencedButOpen).toHaveLength(1);
```

with a shape-based one. Good reason — the snapshot went red on 2026-08-08 at
length 3, and both new entries were the healthy multi-PR-epic case the advisory
note exists to describe. Nothing was wrong; the test was.

PR #116, independently, **moved that entire block** out of the shared test file
into a new `scripts/check-backlog-checkoffs.real-corpus.test.ts`, as part of
making the default `npm test` hermetic. It carried the **pre-fix** assertion
across with it.

The two edit the same region of the same file, so they conflict. The natural
resolution — take #116's version, since #116 owns the file split — **silently
reinstates the assertion #117 had already proven wrong**. Reproduced on the
merged tree, not reasoned about:

```
AssertionError: expected [ { …(4) }, { …(4) }, { …(4) } ] to have a length of 1 but got 3
 ❯ scripts/check-backlog-checkoffs.real-corpus.test.ts:150:38
```

**No gate in this repo can see this.** Both PRs are based on `main`, so both run
the full CI suite and both are green. This is a *different* mechanism from the
"stacked PRs run no CI at all" item logged on 2026-08-08 — that one is about PRs
based on other `team/*` branches matching no `ci.yml` trigger. These run every
check. The general shape:

> When PR A **moves** code that PR B **fixes**, git resolves the text and loses
> the intent. The only artifact that would show it is a tree neither PR's CI
> ever builds.

Logged as a HIGH item. The specific instance is fixed — see below. A third
finding, further down, came out of the Notion reconciliation.

## The falsification failed to fail, and the reason is reported rather than buried

Standard practice here is to prove a fix red before calling it green. Restoring
`toHaveLength(1)` on #116's branch **still passed**. I verified the mutation was
genuinely on disk (`grep` showed it at line 170) before drawing any conclusion,
because a vacuous falsification is worse than none.

It was not a weak test. `referencedButOpen` is *derived from `BACKLOG.md`*, and
#116's branch carries `main`'s backlog, where the real count genuinely **is** 1
— confirmed independently with `npm run check:backlog-checkoffs`. The count only
becomes 3 once #117's `BACKLOG.md` lands.

So the honest statement is: **the assertion is latently wrong, not currently
wrong**, and the real red→green transcript lives on the merged tree, which is
the configuration that matters. That distinction is written into the commit
message on #116 rather than smoothed into a claim of a clean red→green. It also
produced its own LOW item: a "real corpus" test is only as stable as the corpus,
and this corpus is a file every run edits.

### …and then it bit this run, within the hour

The MEDIUM item above was logged at roughly 09:50. The push at 09:58 turned
`build` **red** on #117:

```
AssertionError: expected [ { …(4) } ] to deep equally contain
ObjectContaining{ "branch": "team/2026-08-04-runs-api", … }
 ❯ scripts/check-backlog-checkoffs.test.ts:470:38
```

Same mechanism, one step further along. My check-off removed `runs-api` from
`referencedButOpen`; the real-corpus test **asserts that entry is present**. So
the finding did not just describe a latent hazard — it invalidated a live
assertion in the same commit that described it.

Two things worth stating plainly rather than tidying away:

1. **I missed it locally.** I ran `npm test` on the branch after the edit and
   piped it through `tail -3`, which showed a duration line and no verdict. The
   suite was already red at that moment. Truncating test output to save a few
   lines of context is how you turn a gate into decoration — the same complaint
   this backlog makes about gates people re-run until green. Every verification
   in this run after that point greps for `Test Files|Tests |FAIL` instead.
2. **The fix is not to restore the pin.** The pin was only ever valid while no
   unrelated item mentioned that branch, and this backlog's items routinely name
   other branches when explaining a decision. Both copies now assert the *shape*
   of whatever is reported and pin no branch, with the reasoning inline and a
   note to restore a pin if the gate's matching is ever tightened. The
   detection path is unaffected — it is owned by the synthetic PR #100
   falsification fixture with a fake `ghRunner`, which this assertion never
   protected.

Applied to **both** copies (`check-backlog-checkoffs.test.ts` on #117,
`check-backlog-checkoffs.real-corpus.test.ts` on #116), because the two branches
disagree about which file holds the block and the merged tree has to be green
either way. Re-verified after the fix: 585/585 on #117, 601/601 + 8/8
real-corpus on #116, and the full re-merged queue at **603 unit / 46 smoke / 124
component / 94 content / 8 real-corpus**, build and typecheck clean.

The gate suite caught a defect that four local gate runs and a merge simulation

## Decisions made

1. **Built no features.** Nine open PRs is over throttle. The playbook says spend
   the surplus on planning or stop; I spent it on making the queue mergeable.
2. **Pushed to an existing PR branch rather than opening a tenth.** The fix
   belongs to #116's change, and adding a PR to a jammed queue to fix the jam
   would be self-defeating.
3. **Fixed #116 rather than #117.** Either branch could carry the port, but
   #116 is the one that introduced the stale copy, so the fix belongs with the
   move that caused it — and it makes the resolution safe in *either* merge
   order rather than only one.
4. **Did not restructure the PRs to remove the conflict.** Merging #117 into
   #116 would make the conflict vanish, at the cost of making #116 unreviewable
   in isolation — the exact complaint the existing stacking item raises. A
   documented one-file resolution is cheaper than a permanent structural change.
5. **Did not touch the check-off gate**, despite it missing the incident on its
   own item. Its note already reasoned about that case and the reasoning is
   still sound; changing a gate because it correctly did what it was designed to
   do is how gates get worse.
6. **Left #112 for Dom to close.** Closing another session's PR is not this
   task's call, even with the supersession proven.

## Learnings

**A green check on every PR is not a green check on what you are about to
ship.** This repo has an unusually good gate suite — 12 lanes — and every one of
them was green on both PRs involved. The defect lived in the space between them,
which is the one place nothing looks. Four browser-only bugs taught this project
that a passing suite is not a working page; this is the same lesson one level
up: a passing suite per branch is not a working `main`.

**"Take the file owner's side" is a heuristic about authorship, and the conflict
was about intent.** #116 legitimately owned the file split. Following that rule
would have thrown away a fix whose entire justification was written in a comment
directly above the line being discarded. Git conflict markers show you two
texts; they never show you which one someone already learned something from.

**A falsification that fails to fail is data, not an embarrassment.** The
instinct was to assume a weak test. The real answer was more interesting and
changed what I wrote in the commit message: the assertion is only wrong in
combination, which is the whole thesis of the finding. The 2026-07-29 perf-budget
run set the precedent of reporting a falsification that didn't fail rather than
quietly dropping it; that precedent paid for itself here.

**Bookkeeping about bookkeeping is still real work — up to a point.** This run
found a genuine defect, and it also spent effort checking a box about a gate that
checks boxes. Six lag incidents in, the honest read is that the backlog's
accuracy problem is now costing more than the accuracy is worth, and the queue
being jammed for five days is the actual bottleneck behind all of it. Merging is
the fix; nothing the studio can do unilaterally substitutes for it.
